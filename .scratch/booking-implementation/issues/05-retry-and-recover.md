# 05: Повторная отправка и восстановление

Status: ready-for-agent
State: closed

**Source:** [MVP сервиса бронирования звонков](../../booking-mvp/spec.md).

**What to build:** гость получает определённое согласованной спецификацией
поведение при двойном нажатии, сетевой ошибке и потере ответа после сохранения.
Интерфейс помогает узнать результат или безопасно продолжить запись.

**Blocked by:** 04: [«Подтверждение встречи»](04-confirm-meeting.md).

- [x] Реализована именно выбранная в итоговой спецификации семантика повторной попытки: идентификация запросов, срок действия и поведение при изменении данных, если такие механизмы предусмотрены. Несогласованные гарантии идемпотентности не добавляются.
- [x] Двойное нажатие, повтор после отказа сети и потеря ответа уже сохранённой встречи имеют согласованные наблюдаемые результаты в API и интерфейсе.
- [x] Обработаны две вкладки и конкурентные попытки разных гостей без ослабления запрета пересечений и гарантии единственного победителя.
- [x] Интерфейс различает ожидающие подтверждения, успешные и неуспешные состояния настолько, насколько это предписано спецификацией; не сообщает об отсутствии встречи только из-за потери ответа.
- [x] Доступные повторные действия, восстановление результата либо возврат к выбору времени, сохранение и сброс введённых данных соответствуют согласованным решениям.
- [x] При необходимости расширены контракт, генерируемые типы и защищённое общее состояние; ошибки и результаты совпадают на обеих сторонах.
- [x] HTTP-проверки воспроизводят повтор после сохранения и конкуренцию; браузерные сценарии воспроизводят двойное нажатие и потерю ответа. Проверяется внешний результат, а не внутреннее устройство обработки повторов.
- [x] `mise run check` проходит, Go-тесты выполняются с `-race`.

## Comments

### 2026-11-15 — согласование и запуск пятого среза

Пользователь запросил `implement-spec 05` и разрешил возвращать результат
прежней попытки с обязательным уточнением: два разных гостя с разными
email на один слот не могут получить успех одной встречи; проигравшему
не возвращаются сведения о заявке победителя.

Реализуется повтор той же попытки на текущей странице после сетевой
ошибки или потери ответа. Сохраняются идентификатор и неизменный запрос;
повтор успешной попытки возвращает исходную встречу без дубликата.
Идентификатор связывается с типом, началом, именем и email после
нормализации пробелов; email сравнивается точно, без смены регистра.
Несовпадение любого поля не возвращает прежнюю встречу и не меняет её.
Разные попытки конкурируют за общее время по прежним правилам.

Гарантия действует до перезапуска бэкенда. После определённого отказа
можно исправить контакты или выбрать другой слот с новой попыткой.
При неизвестном результате доступны повторы неизменной попытки; менять
её данные до определённого ответа нельзя. Вкладки независимы.
После закрытия/перезагрузки страницы выбор и контакты не восстанавливаются;
отдельная страница восстановления и хранение контактов в браузере не нужны.

Технический контракт: обязательный UUID `attemptId` в теле подтверждения;
HTTP 201 и та же встреча при успешном повторе, HTTP 400 с `fields.attemptId`
без чужих сведений при несовпадении данных уже сохранённой попытки.
Сохраняются только успешные попытки; ошибки полей/даты/конфликт и отсутствие
типа не связывают идентификатор. Проверка попытки и сохранение входят
в общую критическую секцию календаря.

Общий блокер обзора всей карты снят только для запрошенной задачи 05.
Границы тестирования прежние: HTTP API с управляемым временем и браузер
с настоящим API. Закрытие записи, удаление и Docker остаются следующими задачами.

## Answer

Реализовано в `codex/booking-draft-integration`, коммит `9d5efa6`
(`Recover booking confirmations safely`).

- Контракт `confirmMeeting` требует UUID `attemptId`; обе стороны
  сгенерированы закреплёнными командами. Успешная попытка атомарно
  связывается с типом, моментом начала, обрезанными именем/email.
  Сопоставление email сохраняет регистр, даты сравниваются как моменты.
- Неизменный повтор возвращает HTTP 201 и полное исходное подтверждение
  с теми же ID и ссылкой. Повтор проверяется до актуальных правил окна,
  состояния типа и занятости. Успех удерживается до перезапуска, включая
  окончание встречи и выход её даты из окна; ошибки не запоминаются.
- Иные данные с прежним успешным UUID дают HTTP 400 с `fields.attemptId`
  без сведений о госте или встрече. Разные заявки на один слот сохраняют
  одну встречу; проигравший получает HTTP 409 со свежими слотами,
  без имени/email/ссылки победителя. Повтор по одному лишь слоту
  или email не используется.
- На текущей странице после ошибки сети доступны повторы неизменного
  запроса. Пока результат неизвестен, контакты и выбор заблокированы.
  Повторная ошибка сохраняет неизвестный результат и возможность повтора;
  успех показывает исходную встречу. Определённый отказ позволяет
  исправить данные/слот и создаёт новую попытку. Двойная отправка
  блокируется синхронно, фоновые обновления не сбрасывают попытку.
- Две вкладки независимы; закрытие или перезагрузка сбрасывает локальные
  контакты/выбор/восстановление. Данные попытки не сохраняются в браузере,
  отдельный маршрут восстановления не добавляется.

TDD: воспроизведены падения повторного успеха, защиты от изменённых
данных, ошибок UUID и отсутствующей кнопки восстановления. Внешние HTTP
проверки с управляемым временем охватывают повтор после полуночи,
окончания и выхода окна; одинаковые и различающиеся конкурентные запросы;
поля/формат и отсутствие связывания неуспешных попыток. При 24 запросах
с одним UUID и разными email только один получает своё подтверждение,
остальные — отказ без чужих данных. При 24 независимых пересекающихся
попытках — один успех и 23 конфликта. Повторы одинаковой заявки
возвращают одну идентичность встречи без дубликатов.

Браузер проверяет реальную потерю ответа после сохранения, сбой до доставки,
повторную ошибку, одинаковое тело/UUID при повторах, двойное нажатие,
новый UUID после определённого отказа, две вкладки с разными email,
сброс после перезагрузки и отсутствие сохранения в local/sessionStorage.
