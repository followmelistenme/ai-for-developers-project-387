## Стек

- Бэкенд: Go, Gin; генерация DTO и серверного интерфейса через oapi-codegen.
- Фронтенд: React, TypeScript, Vite, Tailwind CSS и [shadcn/ui](https://ui.shadcn.com/docs/installation/vite).
- Контракт API: TypeSpec → OpenAPI → Go и TypeScript. DTO, SDK-функции и
  Fetch-клиент для TypeScript генерируются через Hey API.

### Контракт API и генерация SDK

Принята связка **Gin + oapi-codegen** для бэкенда и
**Hey API + Fetch** для фронтенда.
Цепочка генерации описана в [ADR-0003](docs/adr/0003-typespec-contract.md).

Контракт редактируется в `api/main.tsp` (операции) и `api/models.tsp` (схемы).
Из TypeSpec генерируется `api/openapi.yaml` в формате OpenAPI 3.0, а из него —

- `backend/internal/api/api.gen.go` — Go DTO запросов и ответов,
  серверный интерфейс и HTTP-обвязка для Gin. Параметры oapi-codegen:
  `models`, `gin-server`, `strict-server`, `embedded-spec`.
- `frontend/src/api/generated/` — TypeScript DTO (`types.gen.ts`),
  SDK-функции по `operationId` (`sdk.gen.ts`), экземпляр клиента
  (`client.gen.ts`) и Fetch runtime (`client/`, `core/`).
  Прикладной код вызывает SDK-функции, например `confirmMeeting`,
  и не собирает HTTP-пути вручную.

После изменения контракта запустите `mise run generate`, затем обновите
обработчики и вызовы клиента при необходимости и выполните проверки.
Используйте именованные модели и стабильные имена операций для `operationId`.
Закреплённые версии генераторов — TypeSpec 1.18.0, oapi-codegen 2.8.2 и Hey API 0.99.0.
Сгенерированные файлы хранятся в Git и обновляются только генерацией:

```bash
mise exec -- npm --prefix api ci
mise run generate
mise run api-check
```

`api-check` повторяет всю цепочку во временной директории и сравнивает
OpenAPI YAML, Go и полное дерево SDK с файлами рабочего дерева. Проверка
входит в `mise run check` и задачу Quality gates в CI. Зависимости
генераторов закреплены отдельно в `api/package.json` и `api/package-lock.json`.
Приложение использует TypeScript 6.0.3.
Для генератора закреплена js-yaml 4.3.2 с исправлениями YAML DoS;
при обновлении Hey API проверьте, можно ли удалить override.

Валидация входящих запросов по OpenAPI подключается отдельно:
`strict-server` и TypeScript-типы не обеспечивают полную проверку данных
во время выполнения. Правила бронирования проверяет бизнес-логика бэкенда;
транспортные DTO отделены от неё и от хранилища в памяти приложения.

Сейчас контракт содержит создание, список, публикацию, окончательное снятие публикации и удаление типов встреч владельца,
а также гостевой каталог, свободные слоты, подтверждение встречи и список
предстоящих встреч владельца.
Входящие запросы проверяются middleware kin-openapi до декодирования
сгенерированным strict-server; бизнес-правила находятся в `internal/meetingtype`
и `internal/meeting`, правила времени — в `internal/availability`,
общее хранилище типов и встреч с mutex — в `internal/memory`.

## Установка

```bash
git clone https://github.com/followmelistenme/ai-for-developers-project-387.git
cd ai-for-developers-project-387
```

### Бэкенд

Go-модуль находится в `backend/go.mod`, настройки линтера и форматирования —
в `backend/.golangci.yml`. Бэкенд использует память процесса: каждый запуск
начинается с пустого списка, перезапуск удаляет все созданные типы встреч,
их публикации и встречи.

Версия Go закреплена в общем `mise.toml` в корне репозитория. После `mise install`
Go-команды выполняются из папки бэкенда:

```bash
cd backend
mise exec -- go mod tidy -diff
mise exec -- go test -race ./...
```

Общие команды `mise run check`, `mise run fix` и `mise run hooks` запускаются
из корня; для Go-проверок `hk.pkl` задаёт рабочую папку `backend`.

### Фронтенд

Node.js управляется через [nvm](https://github.com/nvm-sh/nvm); версия закреплена
в `.nvmrc`. Из корня репозитория:

```bash
nvm install
nvm use
npm --prefix frontend ci
npm --prefix frontend run dev
```

Vite запускает приложение на `http://localhost:5173`. Исходники находятся
в `frontend/src`, алиас `@/` указывает на эту папку. Главная, управление
типами `/owner`, гостевой каталог `/booking` и страницы `/booking/{meetingTypeId}`
используют тёмную палитру.

### Совместный локальный запуск

После `mise install` и `mise exec -- npm --prefix frontend ci` запустите
два терминала из корня репозитория:

```bash
# Терминал 1: API на http://127.0.0.1:8080
mise run backend
```

```bash
# Терминал 2: интерфейс на http://127.0.0.1:5173
mise exec -- npm --prefix frontend run dev
```

Откройте ссылку «Для владельца» в шапке или `/owner`, создайте тип встречи
и сохраните черновик. После перезагрузки страницы он остаётся в списке,
пока работает тот же процесс API. Регистрации и авторизации нет:
управление и owner API доступны любому, кто их откроет. Нажмите «Опубликовать»
на карточке черновика: тип появится в гостевом каталоге `/booking`, доступном
по обеим кнопкам записи с главной. Публикация сохраняется после обновления
страницы, пока работает тот же процесс API. Каждый тип имеет отдельную ссылку
`/booking/{meetingTypeId}`, даже если названия совпадают. Гость видит название,
описание и длительность; черновики недоступны в каталоге и по прямой ссылке.
Действие «Снять публикацию» на `/owner` окончательно закрывает новые записи:
тип получает состояние «Снят с публикации» и исчезает из каталога. По прежней
ссылке и на уже открытом экране гость увидит «Запись на этот тип встречи закрыта».
Все существующие встречи и занятость для остальных типов сохраняются.
Повторная публикация невозможна: для возобновления создайте новый тип,
даже с тем же названием; его ссылка будет отдельной.
Действие «Удалить» доступно в каждом состоянии, если по типу нет ни одной
встречи, включая прошедшие. При наличии встречи API возвращает 409
«Нельзя удалить тип встречи, по которому есть встречи»; опубликованный тип
по-прежнему можно снять с публикации. Удалённый тип исчезает из управления
и каталога, старая ссылка и открытая форма получают 404 без перехода
на одноимённый новый тип. Повтор удаления неизвестного или уже удалённого
ID также возвращает 404; интерфейс убирает устаревшую карточку после повтора.
Проверка всех встреч и удаление атомарны с бронированием: если встреча
сохранена первой, удаление запрещено; если тип удалён первым, новая встреча
не создаётся. Сохранённые успешные попытки продолжают возвращать исходное
подтверждение после отказа в удалении, в том числе когда встреча уже прошла.
На странице типа выберите дату и свободный интервал. Даты и время явно показаны
по Москве независимо от часового пояса браузера. Переключение даты, обновление
слотов, возврат фокуса и сдвиг окна в московскую полночь очищают выбор.
Введённые имя и email сохраняются при обновлении слотов и выборе другого интервала.
Для записи укажите обязательные имя и email и нажмите «Подтвердить запись».
Выбор не резервирует время: сервер заново проверяет весь интервал и атомарно
сохраняет встречу. Если время занял другой гость, интерфейс покажет конфликт
и свежие слоты выбранной даты. Время занято для всех типов встреч.
Подтверждение содержит тип, московскую дату и время, имя, email и копируемую
демонстрационную ссылку `http://localhost/event/{event_id}` с идентификатором
созданной встречи. Сохраните сведения самостоятельно: письма, напоминания
и реальная видеосвязь не реализованы. Возврат фокуса и московская полночь
не сбрасывают ожидающую отправку и успешное подтверждение.

На `/owner` ниже типов встреч расположен общий список будущих и начавшихся
встреч всех типов, от ближайших по времени. Встреча исчезает из ответа API
ровно в момент окончания; кнопка «Обновить встречи», возврат фокуса
и видимости загружают текущий список.
Владелец видит тип, дату, начало и окончание по Москве, имя, email и ссылку
для звонка. Без авторизации этот список и контакты доступны всем, кто откроет
управление; гостевой каталог и свободные слоты контактов не содержат.
После перезагрузки или повторного входа гостевой выбор и контакты начинаются
заново, подтверждение отдельно не восстанавливается. Во время отправки
повторное нажатие не отправляет второй запрос. Если ответ потерян или неизвестен,
интерфейс сообщает, что встреча могла быть создана, и предлагает кнопку
«Повторить подтверждение». Она отправляет ту же попытку с неизменными данными:
если встреча уже сохранена, вернётся исходное подтверждение без дубликата.
При повторном сбое сети можно повторить ещё раз. До определённого ответа
контакты, дата и слот заблокированы; фокус и полночь состояние не меняют.
После 400/409 можно продолжить с новой попыткой, контакты сохраняются. Ответ 404 означает недоступность типа,
410 окончательно закрывает новую запись. При неизвестном результате после снятия
публикации по-прежнему доступен безопасный повтор той же попытки: сохранённая
встреча вернётся исходной, а ещё не доставленная попытка получит 410.
Вкладки создают независимые попытки. Контакты и попытки не записываются
в localStorage/sessionStorage: перезагрузка сбрасывает их, а занятость уже
сохранённой встречи остаётся на сервере.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `BACKEND_HOST` | `127.0.0.1` | Интерфейс прослушивания API |
| `BACKEND_PORT` | `8080` | Порт API |
| `FRONTEND_HOST` | `127.0.0.1` | Интерфейс Vite dev server |
| `FRONTEND_PORT` | `5173` | Порт Vite dev server |
| `API_TARGET` | `http://127.0.0.1:8080` | Адрес API для прокси Vite dev/preview |

Например, `BACKEND_PORT=8090 mise run backend` и
`API_TARGET=http://127.0.0.1:8090 FRONTEND_PORT=5190 mise exec -- npm --prefix frontend run dev`.
Переменные Vite также можно задать в `frontend/.env.local` (не коммитится).
Браузер отправляет запросы на `/api` своего origin; Vite проксирует их
на `API_TARGET`, поэтому CORS не требуется. Для preview порт задаётся
через `npm --prefix frontend run preview -- --port 5190`.

На адресе API доступны `/docs`, `/openapi.json` и `/openapi.yaml`,
без внешних CDN и доступа к интернету. Список —
`GET /api/owner/meeting-types`; создание — `POST /api/owner/meeting-types`.
Создание возвращает 201 с уникальным `id` и `status: "draft"`;
ошибка данных — 400 с `message` и `fields`. Проверяются название
1–100 символов Unicode после обрезки пробелов по краям, необязательное
описание до 500 символов и длительность 15, 30, 45 или 60 минут.
Одинаковые названия разрешены. Публикация —
`POST /api/owner/meeting-types/{meetingTypeId}/publish` без тела запроса:
200 возвращает тип со `status: "published"`, повтор возвращает тот же тип.
Снятие публикации —
`POST /api/owner/meeting-types/{meetingTypeId}/withdraw` без тела запроса
(operationId `withdrawOwnerMeetingType`): 200 с `status: "withdrawn"`, повтор
возвращает тот же тип; черновик — 409, неизвестный ID — 404. Публикация
снятого типа возвращает 409. Снятие и проверка состояния с сохранением встречи
выполняются под общим mutex: сохранённая первой встреча остаётся,
снятие первым запрещает создание новой.
Гостевой API: `GET /api/meeting-types` и `GET /api/meeting-types/{meetingTypeId}`.
Неизвестный идентификатор при публикации, а в гостевом API также черновик,
возвращают 404 с `message`. Снятый тип отсутствует в каталоге; его прямое чтение, слоты и новая попытка
подтверждения возвращают 410 с сообщением «Запись на этот тип встречи закрыта»,
без контактов гостей. Типы в списках идут в порядке создания.
Свободные слоты — `GET /api/meeting-types/{meetingTypeId}/slots` (operationId
`listAvailableSlots`). Необязательный `date=YYYY-MM-DD` — календарная дата
по Москве; без параметра сервер выбирает первый день актуального окна.
Черновик и неизвестный тип возвращают 404; некорректная дата и дата вне окна —
400 с `message` и `fields.date`. Ответ `AvailableSlots` содержит `serverTime`,
`nextWindowUpdate` (момент следующей московской полуночи), `timeZone`,
`windowStart`, `windowEnd`, `selectedDate` и массив `slots` из `AvailableSlot`
с RFC 3339 полями `start`/`end`. Даты окна включительны, времена начала
идут через 30 минут от 09:00; весь интервал должен помещаться до 18:00.
Сервер захватывает текущее время один раз и использует IANA `Europe/Moscow`
со встроенной базой часовых поясов. Слоты используют длительность опубликованного
типа из общего календаря процесса и исключают пересечения с сохранёнными
встречами всех типов. Интервалы полуоткрытые `[start, end)`; соседство допустимо.

Подтверждение — `POST /api/meeting-types/{meetingTypeId}/meetings`
(operationId `confirmMeeting`) с обязательными полями `attemptId` (UUID),
`start` (RFC 3339), `guestName`, `guestEmail`. Окончание и длительность задаёт сервер по опубликованному типу;
передать собственные `end` или `durationMinutes` нельзя. Имя — 1–100 символов
Unicode, email корректного формата — до 254 символов после обрезки краевых
пробелов. Ответ 201 — `Meeting` с типом, датой, началом, окончанием, контактами
и `callUrl`. Ошибки контактов и временных правил — 400 с `fields`; неизвестный
тип и черновик — 404. При пересечении — 409 `BookingConflict`: `message`
и `availability` с актуальными слотами выбранной московской даты, без данных
других гостей. Проверка пересечений и сохранение происходят в одной
критической секции общего хранилища; из конкурентных пересекающихся попыток
успешна одна.

Успешная попытка связывает UUID с типом, моментом начала и контактами.
Имя/email сравниваются после обрезки краевых пробелов, регистр email
сохраняется; эквивалентные RFC 3339 моменты начала равны. Повтор с тем же
UUID и данными возвращает 201 с исходной полной встречей, включая ID и ссылку.
Другие данные или тип с сохранённым UUID получают 400 `fields.attemptId`
без сведений прежнего гостя; это не подтверждение чужой заявки. Новый UUID
при занятом времени получает обычный 409 со свежими слотами без контактов.
Поиск, сравнение и сохранение попытки атомарны под тем же замком календаря.
Запоминаются только успешные попытки; 400/404/409 не связывают UUID.
Проверка повтора предшествует проверкам типа, текущего окна и пересечений.
Успешные попытки остаются в памяти до перезапуска, включая даты вне окна
и закончившиеся встречи; TTL и постоянного хранения нет. Перезапуск
одновременно сбрасывает встречи и попытки.

Список владельца — `GET /api/owner/meetings` (operationId `listOwnerMeetings`),
массив `Meeting` с `end > now`, по возрастанию начала. Контакты выдаются только
в результате подтверждения и этом списке. Восстановление текущей попытки
использует тот же POST; отдельного API или страницы восстановления нет.

### Деплой на Render

Демонстрация первого проекта на Render. [Календарь звонков](https://booking-calendar-386-w289.onrender.com)

#### Подключение Render MCP к Codex

1. В терминале с установленным Codex CLI добавьте сервер:

   ```bash
   codex mcp add render --url https://mcp.render.com/mcp --oauth-client-id codex
   ```

2. В открывшемся браузере войдите в Render и подтвердите доступ через OAuth.
   Если авторизация не началась автоматически, выполните:

   ```bash
   codex mcp login render
   ```

3. Проверьте, что сервер появился в конфигурации:

   ```bash
   codex mcp list
   ```

4. Откройте новый диалог Codex и попросите показать рабочие пространства

### Запуск в Docker

Для сборки и запуска всего приложения одним контейнером используйте
`Dockerfile` в корне репозитория:

```bash
docker build -t booking-app .
docker run --rm -p 8080:8080 booking-app
```

Интерфейс доступен на `http://localhost:8080`, API — на том же origin
по `/api`, документация — `/docs`, `/openapi.json` и `/openapi.yaml`.
Прямое открытие и перезагрузка `/owner`, `/booking` и страниц типов работают.
Образ запускает один Go-процесс без привилегий; данные хранятся в памяти.
Переменная `PORT` задаёт порт внутри контейнера (по умолчанию 8080),
`BACKEND_PORT` имеет приоритет над ней. Например:

```bash
docker run --rm -e PORT=3000 -p 3000:3000 booking-app
```

`FRONTEND_DIR=/app/public` указывает на встроенную сборку интерфейса.
При локальном запуске без `FRONTEND_DIR` бэкенд по-прежнему отдаёт только API.

Для раздельного запуска двух сервисов через Compose:

Нужны Docker Engine и Docker Compose v2 с поддержкой `up --wait`.
Из корня репозитория:

```bash
docker compose up --build --wait --wait-timeout 120
```

Откройте `http://127.0.0.1:5173`: создайте и опубликуйте тип на `/owner`,
выберите его на `/booking`, затем слот и подтвердите запись. Встреча появится
в общем списке владельца на `/owner`. Прямые ссылки и перезагрузка
`/owner`, `/booking` и `/booking/{meetingTypeId}` работают через nginx.
Dockerfile собирают приложение закреплёнными Go 1.27.4 и Node.js 22.22.2;
образы Go, Node, Alpine и nginx закреплены также digest. Зависимости и сборка
выполняются внутри контейнеров, локальные `node_modules` не нужны.

| Переменная Compose | По умолчанию | Назначение |
| --- | --- | --- |
| `FRONTEND_PORT` | `5173` | Порт интерфейса на хосте |
| `BACKEND_PORT` | `8080` | Порт API на хосте |
| `BIND_HOST` | `127.0.0.1` | Адрес публикации обоих портов на хосте |
| `API_TARGET` | `http://backend:8080` | Origin API для nginx внутри сети; без пути и завершающего `/` |
| `TZ` | `UTC` | Часовой пояс окружения контейнеров; календарь всегда `Europe/Moscow` |

Переменные передаются перед командой или через локальный файл `.env`
(не коммитьте секреты). Внутри контейнеров API слушает `0.0.0.0:8080`,
nginx — `0.0.0.0:80`; `BACKEND_PORT` в таблице меняет только порт хоста.
Для других портов и альтернативного сетевого имени API:

```bash
FRONTEND_PORT=15173 BACKEND_PORT=18080 API_TARGET=http://calendar-api:8080 \
  docker compose up --build --wait --wait-timeout 120
```

Тогда интерфейс доступен на `http://127.0.0.1:15173`, прямой API —
на `http://127.0.0.1:18080`. Браузер обращается к относительному `/api`,
nginx проксирует его к `API_TARGET`; имя `backend` или его сетевой alias
`calendar-api` использует только nginx. CORS не требуется. Изменение
`API_TARGET` применяется при пересоздании фронтенда без пересборки:
`docker compose up -d --force-recreate frontend`.

Документация доступна через интерфейс: `http://127.0.0.1:5173/docs`,
`http://127.0.0.1:5173/openapi.json` и `http://127.0.0.1:5173/openapi.yaml`;
те же пути доступны напрямую на порту API `8080`. При других портах
замените их в адресах. Готовность API проверяется чтением списка типов,
а фронтенда — главной и проксированного API. Compose ждёт успешных проверок.
nginx повторно разрешает адрес API через Docker DNS после его пересоздания.

```bash
docker compose logs -f
docker compose restart backend
docker compose up --wait --wait-timeout 120
docker compose down
```

Перезапуск или пересоздание бэкенда очищает все типы, публикации, встречи
и результаты попыток. После обновления `/owner` пуст, прежние ссылки
и повтор прежней попытки получают недоступный тип. Начальных данных,
постоянных томов и внешнего хранилища нет. `down` останавливает оба сервиса.
При изменённых переменных используйте те же значения и для последующих команд.

Автоматическая контейнерная приёмка запускается отдельно:

```bash
mise exec -- npm --prefix frontend ci
mise exec -- npm --prefix frontend run test:install
mise run docker-check
```

Она собирает образы, создаёт отдельный Compose project с пустой памятью
и свободными портами, использует альтернативный `API_TARGET`, UTC в контейнерах
и немосковский пояс браузера. Настоящий браузер проходит создание, публикацию,
запись и список владельца; проверяются документация, прямые маршруты и сброс
после перезапуска/пересоздания API. Сценарий не запускает локальные серверы
и не перехватывает HTTP. При любом исходе он удаляет собственные контейнеры,
сеть и локальные образы; при ошибке печатает их состояние и последние логи.
Существующие сервисы остаются доступны. Не запускайте одновременно обычные
и контейнерные Playwright-тесты: они используют общий каталог результатов.

Сборка, проверка типов и линтинг:

```bash
npm --prefix frontend run build
npm --prefix frontend run typecheck
npm --prefix frontend run lint
```

Готовая сборка сохраняется в `frontend/dist`. Для локального просмотра выполните
`npm --prefix frontend run preview`.

shadcn/ui добавляет исходники компонентов в `frontend/src/components/ui`.
Настройки CLI находятся в `frontend/components.json`. Добавить компонент:

```bash
cd frontend
npm run ui -- add dialog
```

### Тесты фронтенда

Используется [Playwright Test](https://playwright.dev/docs/intro) с Chromium
без окна браузера. После установки npm-зависимостей выполните из корня проекта:

```bash
nvm use
npm --prefix frontend run test:install
npm --prefix frontend test
```

Устанавливать браузер нужно при первой настройке и после обновления Playwright.
В Linux при необходимости добавьте системные зависимости:
`npm --prefix frontend run test:install -- --with-deps` — эта же команда используется в CI.

Перед тестами Playwright запускает настоящий API с пустой памятью
на `127.0.0.1:8081`, проверяет типы, собирает приложение и запускает
`vite preview` на `http://127.0.0.1:4173` с прокси к этому API.
Оба порта должны быть свободны. Сценарии с API дополнительно запускают
собственный настоящий процесс на свободном локальном порту; браузерные запросы
проксируются к нему тестовой fixture. Поэтому пустое состояние и данные
сценария не зависят от порядка тестов. После тестов все запущенные ими процессы
останавливаются. Для браузерных тестов также требуется Go из `mise.toml`.

Дымовой тест `frontend/e2e/smoke.spec.ts` открывает главную страницу, проверяет
успешный HTTP-ответ, видимость заголовка «Календарь звонков» и отсутствие
необработанных ошибок JavaScript. При падении скриншот и трассировка сохраняются
в `frontend/test-results`. `owner.spec.ts` проверяет создание черновика,
перезагрузку, исправление ошибки формы через настоящий API и ширины
320/390 пикселей. HTTP-тесты бэкенда проверяют границы Unicode, нормализацию,
ошибки запросов, независимость новых запусков, параллельное создание и список.
`publication.spec.ts` проверяет публикацию, гостевой выбор, прямые ссылки,
одноимённые типы, недоступность черновиков, загрузку и повтор после сбоя сети.
`slots.spec.ts` проверяет выбор и сброс интервала, смену дат, устаревший ответ,
часовые пояса браузера, загрузку, ошибку/повтор, пустой день, обновление в полночь
и возврат фокуса. Основные сценарии работают с настоящим API; граничные ответы
полуночи и пустого дня моделируются на HTTP-границе браузера. HTTP-тесты слотов
проверяют окно и его сдвиг на том же обработчике, UTC-окружение, смену года,
високосный февраль, сетку для всех длительностей, границы рабочего дня,
ошибки дат и отсутствие резервирования. Управляемое время передаётся только
конструктору приложения `server.NewWithClock`; HTTP и окружение сервера
не предоставляют тестовых часов.
`meetings.spec.ts` проходит запись с главной через настоящий API, копирует
ссылку и проверяет общий список владельца и занятость другого типа. Он также
проверяет настоящий межтиповой конфликт, сохранение контактов, блокировку
ожидающей отправки и синхронного двойного нажатия, восстановление потерянного
после сохранения ответа, повторные обрывы сети до доставки, независимые вкладки,
новые UUID после определённых отказов, сброс при перезагрузке и адаптацию
формы, подтверждения и списка на ширинах 320/390 пикселей. HTTP-тесты встреч
с управляемым временем проверяют контакты, все временные ограничения,
подделанные поля, пересечения и соседство, свежие слоты конфликта без контактов,
одного победителя 24 конкурентных попыток, московскую полночь и границу
окончания начавшейся встречи в хронологическом списке владельца. Проверки
попыток подтверждают каноническое сравнение, UUID-валидацию, отказ без утечки
при изменении данных, одну идентичность конкурентных повторов, изоляцию
разных гостей и повтор после полуночи, окончания встречи и выхода даты из окна.
`withdraw.spec.ts` проверяет окончательное снятие публикации, повтор после сбоя сети,
состояние после перезагрузки, закрытую прежнюю ссылку и независимый одноимённый тип.
Он проверяет отказ старому выбранному интервалу при подтверждении и обновлении слотов,
сохранение встреч владельца и занятости других типов, отложенный/потерянный ответ
и недоставленную попытку при закрытии, включая запоздалый ответ доступности,
а также ширины 320/390 пикселей. HTTP-тесты снятия публикации покрывают необратимость,
идемпотентность, скрытые черновики/неизвестные ID, исходные повторы прошлых и будущих
встреч без раскрытия при изменённых данных, общую занятость и конкурентные
снятие/подтверждение и снятие/публикацию.
HTTP-тесты также проверяют повторную и конкурентную публикацию без дубликатов,
публичную видимость и сохранение полей типа.

### Проверки качества

Установите [mise](https://mise.jdx.dev/getting-started.html) версии 2026.11.8
или новее и Python 3.11 или новее для тестов автотриажа.
Из корня репозитория выполните:

```bash
mise trust
mise install
mise run hooks
mise exec -- npm --prefix frontend ci
mise exec -- npm --prefix api ci
mise exec -- npm --prefix frontend run test:install
mise run check
```

Версии Go, Node.js и инструментов закреплены в `mise.toml`. Версия Node.js
совпадает с `.nvmrc`: при обновлении меняйте оба файла. Для `mise run check`
предварительный `nvm use` не нужен. Команда `mise run check`
запускает все проверки, включая проверку типов, сборку фронтенда и дымовой тест
в Chromium; CI использует ту же команду при push в `main` и для pull request,
еженедельно и при ручном запуске workflow. Отдельный триггер pull request
включён; push ограничен `main`, чтобы изменения ветки PR не проверялись дважды.
Для защиты слияний назначьте `Quality gates` обязательной
проверкой в настройках GitHub ruleset / branch protection.
Отдельная задача `Container acceptance` в том же workflow запускает
`mise run docker-check` на runner с Docker Engine. Её также можно назначить
обязательной. Обычный `mise run check` не требует Docker.

Хук перед коммитом проверяет секреты в индексе, форматирование изменённых Go-файлов,
ESLint при изменениях фронтенда, workflow и инструкции агентам. Перед push проверяется весь проект.
ShellCheck закреплён в `mise.toml` и устанавливается командой `mise install`;
`jactionlint` использует его для анализа shell-команд в workflow локально и в CI.
`mise run fix` применяет только форматирование Go.

Инструменты выбраны по [dev-guardrails (теперь Dev Quality Gates)](https://github.com/mokevnin/dev-quality-gates):
mise управляет окружением, hk — хуками и общим набором проверок, golangci-lint —
Go-линтерами и форматированием, govulncheck — уязвимостями Go, Betterleaks —
секретами, jactionlint с ShellCheck — workflow, agnix — инструкциями агентам.
Существующие ESLint, TypeScript, Playwright и Dependabot сохранены.
Проверка актуальности OpenAPI, Go и SDK входит в общий набор.
Docker проверяется отдельной контейнерной приёмкой. Проверки Terraform,
Kubernetes и миграций БД не добавлены: таких файлов в проекте нет.

ESLint проверяет TypeScript с информацией о типах (`recommendedTypeChecked`),
правила React Hooks и доступность JSX (`jsx-a11y`). Проверяются исходники,
конфигурации и тесты фронтенда; любая ошибка или предупреждение блокирует проверку.
ESLint также входит в `mise run check` и запускается в CI.

TypeScript закреплён на 6.0.3: установленный `typescript-eslint` пока поддерживает
версии ниже 6.1. ESLint закреплён на 9-й ветке, совместимой с `jsx-a11y`.
Для зависимости `@typescript-eslint/typescript-estree` задан узкий npm override
на `minimatch` 11.0.1 с исправлением
[GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249).
При обновлении плагинов проверьте, можно ли обновить TypeScript и ESLint
и убрать override.

В `backend/.golangci.yml` для `golangci-lint` включены `errcheck`, `govet`, `staticcheck`, `ineffassign`,
`unused` и `nolintlint`, а также `gosec` для поиска потенциально небезопасного кода,
`errorlint` для работы с обёрнутыми ошибками и `durationcheck` для ошибок
умножения длительностей. Форматирование проверяет `gofmt`.

Go-проверки включают форматирование, линтер, тесты с `-race`, актуальность
модулей и `govulncheck`. Также проверяются конфигурация и секреты в файлах
и всей истории Git. Сканер уязвимостей и первое получение закреплённого
Go-генератора требуют доступа к сети.

Dependabot еженедельно предлагает обновления Go-зависимостей в `backend/`,
npm-зависимостей в `frontend/` и `api/`, а также GitHub Actions
с задержкой 7 дней после выпуска. Версии инструментов в `mise.toml` обновляются
вручную с повторным запуском проверок. Workflow Хекслета исключён из обновлений:
его нельзя редактировать. `golangci-lint` используется как инструмент разработки
под GPL-3.0; его код не добавляется в приложение.

Пять существующих замечаний к workflow Хекслета согласованы как узкие исключения
в `.github/jactionlint.yaml` до 2027-02-14. После этой даты проверка завершится
ошибкой: потребуется исправление у Хекслета или повторное решение человека.

### Агент в GitHub

настройка и срок действия исключения линтера описаны в
[`.github/workflows/README.md`](.github/workflows/README.md).

variables → Actions → Variables → New repository variable** с именем
`APP_URL`. Workflow проверяет `GET /` и `GET /api/meeting-types`. Пустой список
опубликованных типов встреч допустим. При сбое проверка повторяется с запасом
на пробуждение Render. Отчёт содержит коды HTTP и длительность попыток.

Отчёт сохраняется в сводке GitHub Actions и артефакте `app-monitor-report`.
При подтверждённом сбое OpenCode использует `OPENCODE_API_KEY` и получает отчёт
и выдержки из локальных тикетов `.scratch/` и открытых и закрытых GitHub Issues.
Сверка выполняется без инструментов модели. Права задания — `contents: read`
и `issues: write`. Скрипт проверяет, что список issues актуален перед публикацией.
Совпадение даёт ссылку на существующую задачу. Если сопоставление не завершилось
или OpenCode сомневается, результат остаётся в отчёте для ручной проверки.

Когда workflow попадёт в основную ветку, выберите **Actions → App monitor →
Run workflow** и откройте сводку запуска. Ручной запуск по умолчанию только
сохраняет отчёт. Согласованную новую находку можно опубликовать с опцией
`publish_issues`. В запусках по расписанию публикация включена.

#### Автотриаж новых обращений

[Issue triage](.github/workflows/issue-triage.yml) запускается при открытии
GitHub Issue, в том числе от внешнего автора. Он пропускает обращения ботов,
аккаунтов младше 30 дней и задачи с метками `ready-for-agent`, `ready-for-human`,
`needs-info`, `wontfix`.
Перед публикацией воркфлоу сверяет актуальные метки и проверяет, был ли уже
оставлен комментарий автотриажа.

Воркфлоу использует закреплённую версию OpenCode CLI и секрет `OPENCODE_API_KEY`.
Отдельная конфигурация отключает инструменты OpenCode. Модель получает первые
256 символов заголовка и 6000 символов описания и выбирает категорию (`bug` или
`enhancement`) и до трёх вопросов из фиксированного списка. Если есть вопросы,
воркфлоу рекомендует `needs-info`, иначе — `needs-triage`.

Рекомендация публикуется одним комментарием. Воркфлоу использует встроенный
токен GitHub Actions с правами `contents: read` для чтения репозитория и
`issues: write` для публикации комментария. Метки назначает сопровождающий,
а статусы задач реализации ведутся в [локальном трекере](docs/agents/issue-tracker.md).

После слияния в `main` откройте два тестовых issue. У первого оставьте метки
пустыми и проверьте появление одного комментария с разбором. Если метки
`ready-for-agent` ещё нет, сначала создайте её в **Issues → Labels**. Назначьте
её второму issue при создании и убедитесь, что автотриаж его пропустил.
Оба сценария можно проверить на странице [Actions → Issue triage](https://github.com/followmelistenme/ai-for-developers-project-387/actions/workflows/issue-triage.yml).

#### Независимое ревью pull request

[PR review](.github/workflows/pr-review.yml) запускается на `pull_request` при
открытии, новом коммите, повторном открытии или переводе PR из черновика.
Ревью получает готовый PR из ветки этого репозитория в ветку по умолчанию.
Запуски от Dependabot пропускаются.
GitHub отменяет предыдущий запуск для того же PR при поступлении нового события.
Тайм-аут задания — пять минут.

Воркфлоу читает критерии из [`REVIEW.md`](REVIEW.md) и скрипты из коммита базовой
ветки. При первом добавлении воркфлоу шаг ревью пропускается до попадания этих
файлов в базовую ветку. OpenCode использует `OPENCODE_API_KEY`, получает описание
PR и выдержку до 30 файлов и 24 000 символов патчей, работает без инструментов и
внешних плагинов. В отчёте отмечается неполное покрытие диффа.

До вызова модели шаг резервирует один из трёх запусков на PR. Счётчик хранится
в комментарии бота и сохраняется при обновлениях PR и повторном запуске задания.
Зарезервированная попытка учитывается даже при отмене или ошибке. После исчерпания
лимита шаги установки и вызова модели пропускаются.

Права задания — `contents: read` для чтения базы и `pull-requests: write` для
комментария. Перед публикацией повторно проверяются коммиты PR и базы, чтобы
результат относился к актуальному диффу. В комментарии указан проверенный коммит.
Сценарии с авторевью видны во вкладке **Actions → PR review**. Для нового PR
заполните [шаблон](.github/PULL_REQUEST_TEMPLATE.md) и укажите проверки, риски и
способ отката.

## Использование

«Запись на звонок» — упрощённый сервис бронирования времени по мотивам [Cal.com](https://cal.com/). В приложении один заранее заданный владелец календаря; авторизации, личных кабинетов и интеграций с внешними календарями нет.

### Сценарий записи

1. Владелец создаёт тип встречи «Знакомство», задаёт описание и длительность 30 минут и публикует его для записи.
2. Гость без регистрации выбирает «Знакомство» и открывает календарь со свободными слотами на ближайшие 14 дней.
3. Гость выбирает, например, завтрашний слот 10:00–10:30 и подтверждает запись.
4. Сервис повторно проверяет доступность интервала и сохраняет встречу. Гость видит подтверждение, а занятое время становится недоступным для всех типов встреч.
5. В списке предстоящих встреч владельца появляется запись «Знакомство» с датой и временем 10:00–10:30. Список объединяет встречи всех типов.

### Правила записи

- Часовой пояс календаря — `Europe/Moscow`; все даты и время отображаются в нём.
- Окно записи — 14 календарных дней, начиная с завтрашнего дня: от завтра до сегодня + 14 дней включительно. Оно ежедневно сдвигается на один день.
- Владелец доступен ежедневно с 09:00 до 18:00. Встреча должна полностью помещаться в эти часы.
- Длительность слота равна длительности выбранного типа встречи. Доступные старты идут с шагом 30 минут от 09:00; показываются только слоты, целиком попадающие в рабочие часы и не пересекающиеся с существующими встречами.
- Любое пересечение запрещено, в том числе частичное и между разными типами встреч. Интервалы учитываются как `[начало, конец)`: следующая встреча может начаться ровно в момент окончания предыдущей.
- Проверка пересечений и сохранение выполняются атомарно: из двух одновременных запросов на пересекающиеся интервалы успешен только один. Второй гость получает сообщение, что время уже занято, и обновлённый список свободных слотов.
