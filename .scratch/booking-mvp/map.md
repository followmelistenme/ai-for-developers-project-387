# Спецификация MVP сервиса бронирования звонков

Labels: wayfinder:map

## Destination

Согласованная спецификация MVP сервиса бронирования звонков, достаточная
для реализации без открытых продуктовых и архитектурных вопросов.
Итоговый документ — `spec.md` рядом с этой картой, со ссылками на решения.

## Notes

- Карта планирует работу. Реализация приложения, написание OpenAPI-контракта,
  настройка генераторов и Docker выполняются после прохождения карты.
  Прототипы допустимы как материалы для обсуждения.
- Исключение, подтверждённое пользователем 2026-11-15: создание и список
  черновиков реализуются отдельным первым срезом после согласования
  `/owner` и API черновиков. Полное согласование MVP не блокирует этот срез;
  остальные открытые решения карты остаются открытыми.
- Пользователь продолжил реализацию запросом второго среза — публикации
  и выбора типа встречи. Для него достаточно согласованного жизненного
  цикла и завершённого первого среза; остальные открытые решения карты
  не блокируют эту узкую задачу и не закрываются автоматически.
- Запрос третьего среза разрешает расчёт и выбор свободного слота
  по уже заданным правилам московского времени. Создание встречи,
  обработка конфликтов и повторов остаются следующими срезами.
- Запрос четвёртого среза разрешает подтверждение встречи, атомарную
  проверку пересечений и общий список владельца. Для списка согласованы
  будущие и идущие встречи, ближайшие сверху; поля — тип, московская
  дата и интервал, имя, email, ссылка звонка. Повторы и восстановление
  результата остаются отдельной задачей.
- Пятый запрошенный срез добавляет повтор неизменной попытки до перезапуска
  бэкенда. Пользователь особо подтвердил изоляцию разных гостей: второй
  email никогда не получает подтверждение первого. Восстановление ограничено
  текущей страницей; остальные открытые вопросы карты не блокируют этот срез.
- Шестой запрошенный срез реализует согласованное окончательное снятие
  публикации, сохраняя встречи, общую занятость и повторы уже успешных
  попыток. Обзор всей карты не блокирует этот срез; удаление и Docker
  остаются следующими задачами реализации.
- Седьмой запрошенный срез добавляет удаление типа без единой встречи
  в любом состоянии, атомарное с подтверждением. Общий обзор карты
  не блокирует эту задачу; Docker остаётся отдельным срезом.
- Восьмой запрошенный срез разрешает совместный Docker-запуск,
  проксирование API и документации через адрес фронтенда и отдельную
  контейнерную приёмку в CI. Остальные обзорные вопросы карты
  автоматически не закрываются этим запросом.
- Границы подтверждены пользователем 2026-11-15: создание и публикация типов
  встреч, запись гостя, просмотр предстоящих встреч владельцем календаря.
  В карту входят данные, поведение API, конкурентное бронирование, ошибки,
  критерии приёмки, требования к локальному запуску и Docker.
- Исходные ограничения не переоткрываем:
  [README](../../README.md), [AGENTS.md](../../AGENTS.md),
  [глоссарий](../../GLOSSARY.md),
  [OpenAPI-first](../../docs/adr/0001-openapi-contract-first.md).
  Один владелец календаря, хранение в памяти, правила московского времени
  и атомарного бронирования обязательны.
- [Согласованный интерфейс главной](../homepage/spec.md) — основа новых
  экранов: русский язык, тёмная палитра с синим акцентом, мобильная адаптация.
  Переработка главной не требуется; переход с неё должен вести к настоящей записи.
- Каждая сессия читает карту и применяет `wayfinder`, `grilling`
  и `domain-modeling`; для задач `Type: prototype` также `prototype`.
  Новые термины фиксируются в глоссарии по мере согласования.
- Используем [локальный трекер](../../docs/agents/issue-tracker.md).
  Дочерние задачи находятся в `issues/`; карта не дублирует их открытый список.
  Следующая задача — первая по номеру со статусом `open`, у которой все
  зависимости `resolved`. Перед работой установить `Status: claimed`;
  при завершении сохранить `## Answer`, установить `Status: resolved`
  и добавить сюда ссылку с кратким результатом. За сессию решаем одну задачу.
- Внешнее исследование пока не требуется: первые решения опираются
  на локальные требования и предпочтения пользователя. Если обнаружится
  зависимость от внешнего факта, создаётся отдельная задача `research`.
- Карта завершена, когда все дочерние задачи разрешены, туман разобран
  или явно исключён из объёма, а пользователь согласовал итоговую спецификацию.

## Decisions so far

- [Как владелец управляет типами встреч в MVP?](issues/01-meeting-type-lifecycle.md):
  согласованы данные и необратимый жизненный цикл без редактирования;
  снятие публикации сохраняет встречи, удаление допустимо только без встреч.
- [Какие данные гостя нужны для записи и самого звонка?](issues/02-guest-contact-data.md):
  обязательны имя и email; подтверждение содержит копируемую демонстрационную
  ссылку на встречу, сведения гость сохраняет самостоятельно.

- [Что происходит при повторном подтверждении записи?](issues/03-booking-retries.md):
  повтор идентификатора и тех же данных возвращает исходную встречу;
  иные данные не раскрывают прежнего гостя, разные попытки конкурируют.
  Срок — до перезапуска бэкенда, восстановление на текущей странице.

## Not yet specified

- Общая проверка жизненного цикла выполнена в срезах 06/07: закрытие
  сохраняет прежний успешный повтор, наличие любой встречи запрещает
  удаление типа. Общий mutex предотвращает создание встречи с исчезнувшим
  типом. Техническое ревью всей реализации завершено 2026-11-16:
  [Standards и Spec](../booking-implementation/review.md), 0 оставшихся
  замечаний. Обзор продуктовой карты и матрицы приёмки остаётся открытым.
- Расхождения между будущими прототипами, моделью данных и API ещё не видны.
  По мере сверки выделять конкретные противоречия в отдельные задачи;
  перед итоговым согласованием подтвердить, что неразобранных областей нет.

## Out of scope

- Отмена и перенос встреч — пользователь исключил из MVP.
- Уведомления и встроенная видеосвязь — пользователь исключил из MVP.
  Страница по демонстрационной ссылке для звонка и отдельная страница
  восстановления подтверждения также исключены при согласовании
  [данных гостя и ссылки](issues/02-guest-contact-data.md).
- Авторизация, личные кабинеты, несколько владельцев, внешние календари,
  внешние БД, ORM и миграции — исключены исходными требованиями.
- Реализация приложения и эксплуатация публичного сервиса — за пределами
  результата этой карты; здесь согласуются требования к реализации и запуску.
