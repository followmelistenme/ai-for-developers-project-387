# MVP сервиса бронирования звонков

## Problem Statement

Гостю нужно выбрать удобное время звонка без регистрации и переписки
о свободных часах. Владельцу календаря нужно предлагать разные типы встреч
и видеть предстоящие звонки в одном списке. Параллельная запись гостей
не должна приводить к пересекающимся встречам.

Сейчас приложение представляет сервис на главной странице, но переход
к записи открывает заглушку. Бронирование, управление типами встреч
и серверная часть ещё не реализованы.

## Solution

Предоставить сервис с одним заранее заданным владельцем календаря.
Владелец создаёт и публикует типы встреч. Гость выбирает опубликованный
тип, свободный слот и подтверждает запись. Сервис проверяет ограничения,
сохраняет встречу и исключает занятое время из доступности всех типов.
Владелец видит общий список предстоящих встреч.

Сохранить согласованный русский интерфейс, тёмную палитру с синим акцентом
и мобильную адаптацию. Оба сервиса должны запускаться локально и совместно
в Docker. Данные хранятся в памяти и очищаются при перезапуске бэкенда.

Документ синтезирует согласованные требования; неразрешённые решения
перечислены в Further Notes и не заменены предположениями.

## Implementation Decisions

- Продукт включает одного заранее заданного владельца календаря, гостей
  без регистрации, управление типами встреч, запись и общий список
  предстоящих встреч. Управление владельца доступно по `/owner`,
  в шапке ссылка «Для владельца». Первый экран содержит список типов
  встреч и кнопку «Создать тип встречи», пустое состояние предлагает
  создать первый тип. Авторизация не добавляется.
- Для первого среза согласованы `GET /api/owner/meeting-types` со списком
  типов, включая пустой, и `POST /api/owner/meeting-types` для создания
  из названия, необязательного описания и длительности в минутах.
  Сервер назначает уникальный идентификатор и состояние `draft`;
  создание возвращает HTTP 201 с созданным типом, ошибки данных —
  HTTP 400 с сообщением и ошибками по полям. Этот срез разрешён
  к реализации до завершения всей карты.
- Второй запрошенный срез добавляет публикацию из управления владельца,
  каталог на `/booking` и отдельную страницу `/booking/{meetingTypeId}`.
  Для него выбран `POST /api/owner/meeting-types/{meetingTypeId}/publish`
  без тела: HTTP 200 с типом, в том числе при повторе; неизвестный тип —
  HTTP 404. Гостевые `GET /api/meeting-types` и
  `GET /api/meeting-types/{meetingTypeId}` предоставляют только опубликованные
  типы; неизвестный тип и черновик в гостевом API возвращают HTTP 404.
  Выбор времени и подтверждение добавляются следующими срезами.
- Третий запрошенный срез добавляет выбор даты и свободного интервала
  на странице опубликованного типа. `GET /api/meeting-types/{meetingTypeId}/slots`
  принимает необязательную дату YYYY-MM-DD, по умолчанию первый день
  текущего окна. Ответ сообщает серверное время, Europe/Moscow, даты
  начала/окончания окна, выбранную дату и интервалы в RFC 3339.
  Неверная дата или выход за окно — HTTP 400, черновик или неизвестный тип —
  HTTP 404. Смена даты очищает слот, перезагрузка начинает выбор заново;
  устаревший выбор очищается при обновлении окна. Выбор не резервирует время.
- Четвёртый запрошенный срез добавляет подтверждение с обязательными
  именем и email, атомарное сохранение встречи и исключение занятых
  интервалов для всех типов. Список владельца на `/owner` включает
  будущие и идущие встречи, пока окончание позже текущего времени;
  сортируется по началу, ближайшие сверху. Пользователь подтвердил поля:
  тип, дата и интервал по Москве, имя, email, ссылка звонка.
  Повторы и восстановление уточняются пятым срезом.
- Пятый срез добавляет безопасный повтор на текущей странице: идентификатор
  успешной попытки и те же тип/начало/имя/email возвращают исходную встречу
  до перезапуска бэкенда, даже после выхода даты из окна. Имя/email
  обрезаются по краям; email сравнивается точно. Другие данные с прежним
  идентификатором получают отказ без сведений о прежнем госте. Два гостя
  с разными email конкурируют за слот; проигравший не получает встречу
  победителя. Повтор неизвестного результата сохраняет неизменный запрос,
  определённый отказ позволяет новую попытку с исправленными данными.
  Вкладки независимы; после закрытия/перезагрузки контакты и попытка
  не восстанавливаются. Успешные попытки сбрасываются вместе со встречами
  при перезапуске, без отдельного срока истечения или страницы восстановления.
- Шестой запрошенный срез добавляет окончательное снятие публикации
  на `/owner`. Состояние `withdrawn` не возвращается в черновик и
  не публикуется снова. Встречи и общая занятость сохраняются;
  каталог исключает закрытый тип, прямая ссылка и новая запись сообщают
  «Запись на этот тип встречи закрыта» без перехода на одноимённый тип.
  Новое подтверждение и снятие упорядочены общей критической секцией.
  Повтор уже сохранённой успешной попытки возвращает исходную встречу
  и после снятия публикации; это не новое бронирование.
- Седьмой запрошенный срез добавляет удаление на `/owner` из любого
  состояния при отсутствии всех встреч, включая прошедшие.
  `DELETE /api/owner/meeting-types/{meetingTypeId}` (`deleteOwnerMeetingType`)
  возвращает HTTP 204; неизвестный/уже удалённый ID — HTTP 404, наличие
  любой встречи — HTTP 409 с сообщением «Нельзя удалить тип встречи,
  по которому есть встречи». Для опубликованного типа после отказа
  остаётся доступным снятие публикации. Проверка всех встреч и удаление
  атомарны с подтверждением: встреча, сохранённая первой, запрещает удаление;
  удалённый первым тип запрещает создание встречи. Прежний ID не заменяется
  одноимённым типом. Повтор DELETE после потери успешного ответа может
  получить 404; интерфейс убирает устаревшую карточку в обоих случаях.
- Восьмой запрошенный срез добавляет многоэтапные Dockerfile и Compose
  с проверками готовности. Браузер обращается к адресу фронтенда;
  Nginx проксирует `/api`, `/docs`, `/openapi.json`, `/openapi.yaml`
  к `API_TARGET` внутри контейнерной сети. CORS не нужен при едином origin.
  SPA поддерживает прямое открытие и перезагрузку маршрутов. Хостовые
  `FRONTEND_PORT`/`BACKEND_PORT` по умолчанию 5173/8080, привязка
  `BIND_HOST` — 127.0.0.1; внутренние порты фронтенда/API — 80/8080.
  Контейнерный `API_TARGET` по умолчанию `http://backend:8080`, это адрес
  для прокси, а не для браузера. Переменные и команды описаны в README.
  Контейнерная приёмка — отдельный `mise run docker-check` и job CI;
  `mise run check` сохраняет обычные проверки без требования Docker Engine.
- Фронтенд использует существующий React, TypeScript, Vite, Tailwind CSS
  и shadcn/ui. Главная сохраняется; временная запись заменяется настоящей.
  Новые экраны следуют согласованному русскому языку и визуальному стилю.
- Бэкенд использует Go и Gin. HTTP-обработчики и транспортные DTO
  отделяются от бизнес-правил и хранения данных. Точное деление модулей
  и интерфейсы ещё предстоит согласовать.
- Принят OpenAPI-first по ADR-0001: сначала общий контракт, затем генерация
  для обеих сторон. Go генерируется через oapi-codegen с `models`,
  `gin-server`, `strict-server`, `embedded-spec`; TypeScript — через
  Hey API: TypeScript DTO, SDK-функции по operationId и Fetch-клиент
  (ADR-0002, решение пользователя от 2026-11-16).
- Версии генераторов фиксируются; результаты генерации хранятся в Git,
  не редактируются вручную, их актуальность проверяется в CI.
  Контракт содержит стабильные operationId, именованные схемы,
  описания и ожидаемые ошибки. Операции создания и списка черновиков
  согласованы для первого среза; схемы и остальные операции уточняются
  по мере прохождения карты.
- Входящие HTTP-запросы валидируются по OpenAPI отдельно от strict-server
  и TypeScript-типизации. Все ограничения проверяются на бэкенде,
  независимо от проверок в интерфейсе.
- API публикует `/openapi.json`, `/openapi.yaml` и документацию `/docs`.
- Приложение хранит типы встреч и встречи только в памяти процесса.
  Запуск и перезапуск дают пустое состояние без автоматически созданных
  примеров. Прежние ссылки после перезапуска не позволяют записаться
  на прежние типы. Владельцу предлагается создать первый тип встречи.
- Название типа встречи обязательно: 1–100 символов после обрезки
  пробелов по краям; одинаковые названия допустимы. Описание необязательно,
  обычный текст до 500 символов. Длительность — 15, 30, 45 или 60 минут.
- Сохранение корректной формы создаёт черновик. Сохранённые данные
  не редактируются ни в одном состоянии; изменение требует нового типа.
- Жизненный цикл необратим: черновик → опубликован → снят с публикации.
  Черновики недоступны гостям для просмотра и записи. Публикация —
  отдельное действие. Снятие публикации окончательно, не возвращает
  тип в черновик и не допускает повторной публикации.
- В календаре одновременно может быть не более пяти опубликованных
  типов встреч. Владелец может сохранять черновики при заполненном лимите.
  Снятие публикации или удаление опубликованного типа освобождает место.
  Бэкенд проверяет лимит при переходе из черновика в опубликованный тип
  и при отказе сохраняет черновик. Повтор запроса для уже опубликованного
  типа возвращает этот тип даже при заполненном лимите.
  Кнопка «Опубликовать» остаётся доступной при заполненном лимите.
  При отказе из-за лимита рядом с черновиком появляется сообщение
  «Уже опубликовано 5 типов встреч. Снимите публикацию с одного из них
  и попробуйте снова».
- Новый тип получает отдельную ссылку, даже при совпадении названия.
  Старые ссылки не переводят гостя автоматически на новый тип.
- Тип можно окончательно удалить из любого состояния только при отсутствии
  любых встреч по нему, включая прошедшие. Снятие публикации сохраняет
  встречи и их занятое время для всех типов.
- Часовой пояс календаря — Europe/Moscow независимо от окружения.
  Окно записи ежедневно сдвигается: завтра…сегодня + 14 дней включительно.
  Рабочие часы ежедневно 09:00–18:00; встреча должна помещаться целиком.
- Начала встреч образуют сетку с шагом 30 минут от 09:00 независимо
  от длительности типа. Свободный слот — интервал длиной выбранного типа,
  а не отдельная отметка начала.
- Интервалы учитываются как [начало, конец). Любое пересечение,
  включая частичное и между разными типами, запрещено; соседние встречи
  допустимы. Показ слота и его выбор не резервируют время.
- Общее состояние защищено от конкурентного доступа. Проверка пересечений
  и сохранение встречи выполняются в одной критической секции с общим
  хранилищем для всех типов. При конкурентных пересекающихся запросах
  успешен один, проигравший получает сообщение и обновлённые слоты.
- При подтверждении проверяются существование и публикация типа вместе
  с правилами записи. После снятия публикации возвращается сообщение
  «Запись на этот тип встречи закрыта»; по удалённому типу запись невозможна.
- Бронирование согласовано со снятием публикации: сохранённая первой
  встреча остаётся, после снятия публикации новые встречи не создаются.
  Проверка отсутствия встреч и удаление типа также согласованы
  с конкурентным сохранением встречи.
- Успешная запись создаёт встречу с типом, датой, временем начала
  и окончания, обязательными именем и email гостя. Имя — 1–100 символов,
  email — до 254 символов после обрезки пробелов по краям; формат email
  проверяется. Проверка обоих полей выполняется на бэкенде, подтверждения
  email письмом нет. Телефон и комментарий не добавляются.
- Имя и email сохраняются во встрече и показываются в списке владельца
  и подтверждении гостя; гостевой каталог и ответы со свободными слотами
  не содержат контактов. При отсутствии авторизации данные интерфейса
  владельца доступны любому, кто его откроет; это согласованное ограничение.
- Ссылка для звонка формируется из константы по шаблону
  `http://localhost/event/{event_id}`, где event_id — идентификатор
  созданной встречи, а не её типа. Ссылка демонстрационная; страница
  по ней и реальная видеосвязь не реализуются. Настройка ссылки через
  окружение и редактирование в интерфейсе не нужны.
- Подтверждение показывает имя и email гостя, тип встречи, дату,
  московское время и ссылку с возможностью копирования. Экран просит
  самостоятельно сохранить сведения: письма и напоминания не отправляются,
  отдельная страница восстановления подтверждения не предусматривается.
- Для обоих сервисов нужны Dockerfile и совместный запуск через Compose.
  Порты и адрес API настраиваются через окружение; сервисы доступны
  в контейнерной сети, API доступен браузеру. Команды и переменные
  документируются. Для восьмого среза выбраны единый origin с Nginx-прокси,
  проверка готовности, внутренние/хостовые порты и отдельная контейнерная приёмка.

## Testing Decisions

- Проверять внешнее поведение: доступные действия, ответы, созданные
  встречи и свободные слоты. Не привязывать тесты к внутренним структурам,
  отдельным блокировкам, именам вспомогательных функций или CSS-классам.
- Уже существует браузерная граница Playwright: переходы с главной,
  возврат, перезагрузка страницы записи, отсутствие ошибок JavaScript
  и горизонтальной прокрутки на ширинах 320 и 390 пикселей. Сохранить
  применимые проверки; ожидание временной заглушки обновить при реализации.
- Предлагаемая основная граница приёмки — существующие браузерные сценарии
  с настоящим API: владелец создаёт и публикует тип, гость записывается,
  владелец видит встречу, занятый интервал исчезает для всех типов.
  Сюда же относятся формы, закрытие записи, пустые состояния и ошибки
  после согласования их поведения.
- Предлагаемая дополнительная граница — HTTP API бэкенда с общим
  хранилищем и управляемым текущим временем. На ней проверять временные
  границы и конкурентные запросы без зависимости от браузерных таймингов.
  Имеющийся проект пока не содержит такой серверной тестовой границы.
  Эти границы подтверждены для первого среза при согласовании задачи
  «Создание черновика». Матрица приёмки всего MVP уточняется отдельно.
- Обязательны проверки московской календарной даты при другом часовом
  поясе окружения, сдвига окна в полночь, отказа на сегодня и за пределами
  четырнадцатого дня, допустимости завтра и четырнадцатого дня.
- Проверить начало в 09:00, окончание ровно в 18:00, отказ при выходе
  за рабочие часы и вне сетки стартов, все четыре разрешённые длительности.
  Например, встреча на 30 минут может начаться в 17:30, а на 45 минут — нет;
  длительность 15 минут не добавляет начало в 09:15.
- Проверить соседние интервалы, полное и частичное пересечение,
  вложенный интервал и пересечение разных типов. При конкурентных
  пересекающихся запросах сохраняется ровно одна встреча; проигравшему
  доступны сообщение о конфликте и обновлённые слоты.
- Проверить границы данных типа встречи, разрешённые длительности,
  одинаковые названия, недоступность черновика гостю, отдельную публикацию,
  необратимость снятия публикации и запрет редактирования во всех состояниях.
- Проверить публикацию пятого типа, отказ для шестого с сохранением
  черновика, успешный повтор публикации уже опубликованного типа при
  заполненном лимите и повтор отказанной публикации после снятия или
  удаления одного из пяти. Из двух запросов на публикацию разных
  черновиков при четырёх опубликованных типах успешен ровно один.
  Интерфейс показывает причину отказа рядом с черновиком.
- Проверить удаление без встреч и отказ при наличии будущей или прошедшей
  встречи, сохранение встреч и занятости после снятия публикации,
  отсутствие автоматического перехода на одноимённый новый тип.
- Проверить оба порядка конкурентных действий: бронирование до и после
  снятия публикации, а также бронирование одновременно с удалением типа.
  Проверять допустимые результаты и целостность данных, а не реализацию блокировки.
- Проверить обязательность и границы имени и email, обрезку пробелов,
  отказ при неверном формате email, сохранение и показ данных в списке
  владельца и подтверждении гостя, отсутствие контактов в каталоге и слотах.
  Подтверждение содержит копируемую демонстрационную ссылку с идентификатором
  созданной встречи и просьбу самостоятельно сохранить сведения.
- Проверить пустой запуск, сброс данных при перезапуске и недействительность
  прежних ссылок; доступность API и документации локально и в Docker,
  корректную работу адреса API из браузера и независимость времени от окружения.
- Сохраняются обязательные проверки проекта: общий `mise run check`,
  Go-тесты с `-race` при появлении кода, типизация, линтинг, сборка,
  браузерные сценарии и проверка актуальности генерации при её добавлении.
  Для пятого среза дополнительно проверяются потеря ответа после сохранения,
  ошибка до доставки, повторная ошибка сети, двойное нажатие, две вкладки,
  неизменный идентификатор/запрос при повторе и новый после определённого отказа.
  HTTP-проверки подтверждают один ID встречи при повторе, сохранение результата
  после сдвига окна/окончания встречи и отказ без чужих сведений при смене
  типа, времени, имени или email с прежним идентификатором. Конкуренция разных
  гостей сохраняет единственного победителя; одинаковые повторы одной попытки
  могут вернуть несколько успешных ответов об одной сохранённой встрече.

## Out of Scope

- Авторизация, регистрация, личные кабинеты и несколько владельцев календаря.
- Интеграции с внешними календарями.
- Отмена и перенос встреч.
- Уведомления, подтверждение email письмом, напоминания и встроенная
  видеосвязь. Ссылка для звонка демонстрационная; страница по ней
  и отдельная страница восстановления подтверждения не реализуются.
- Телефон и комментарий гостя; настройка ссылки для звонка через окружение
  или интерфейс.
- Внешние базы данных, ORM, миграции и сохранение данных между перезапусками.
- Редактирование сохранённых типов встреч, возврат снятого с публикации
  типа в черновик и его повторная публикация.
- Переработка уже согласованной презентационной главной.
- Публичное размещение и эксплуатация сервиса. Локальный и Docker-запуск
  входят в MVP.
- Написание приложения, контракта, генераторов и Docker-конфигурации
  в рамках текущего запроса: сейчас публикуется спецификация.

  исходное состояние: главная была реализована, настоящая запись и бэкенд
  отсутствовали. В первом срезе добавлен бэкенд создания и списка черновиков
  и интерфейс владельца; во втором реализованы публикация, гостевой каталог
  и отдельная страница типа. В третьем реализованы расчёт доступности
  и выбор даты и свободного интервала по Москве. В четвёртом добавлены
  подтверждение встречи, исключение занятых интервалов всех типов,
  конфликт с актуальными слотами и список будущих/идущих встреч владельца.
  Пятый срез реализует повтор неизменной попытки и возврат исходного
  подтверждения без дубликатов, с изоляцией разных гостей. Шестой добавляет
  окончательное снятие публикации, закрытые гостевые ссылки и сохранение
  встреч, общей занятости и результатов успешных попыток. Седьмой добавляет
  удаление без каких-либо встреч, терминальную недоступность старого ID
  и атомарность удаления с подтверждением. Восьмой добавляет совместный
  Docker-запуск и отдельную приёмку собранных контейнеров в CI.
- Решено: [«Какие данные гостя нужны для записи и самого звонка?»](issues/02-guest-contact-data.md).
  Обязательные имя и email, их ограничения, показ сведений и демонстрационная
  ссылка на созданную встречу согласованы. Гость самостоятельно сохраняет
  подтверждение; реальная связь участников внутри MVP не реализуется.
- Решено: [«Что происходит при повторном подтверждении записи?»](issues/03-booking-retries.md).
  Разрешён повтор той же попытки с теми же данными на текущей странице
  до перезапуска бэкенда. Разные гости никогда не получают чужой результат.
- Открыто: [«Как владелец открывает управление и просматривает предстоящие встречи?»](issues/04-owner-experience.md).
  Вход и экран черновиков согласованы для первого среза; в четвёртом
  согласованы поля, порядок и учёт идущих встреч. Остальные действия
  владельца реализуются следующими срезами.
- Открыто: [«Как гость проходит запись и восстанавливается после ошибок?»](issues/05-guest-experience.md).
  Каталог и отдельная страница опубликованного типа входят во второй
  запрошенный срез. Выбор даты и слота добавлен третьим срезом,
  подтверждение и обработка конфликта — четвёртым. Повторы неизвестного
  результата на текущей странице согласованы для пятого среза;
  отдельной страницы или восстановления после перезагрузки не требуется.
- Открыто: [«Какой API покрывает согласованные сценарии MVP?»](issues/06-api-semantics.md).
  Создание и список черновиков согласованы для первого среза;
  публикация и чтение опубликованных типов добавлены вторым срезом,
  слоты с серверными метаданными окна — третьим, подтверждение,
  конфликт с актуальной доступностью и список владельца — четвёртым.
  Пятый добавляет обязательный attemptId и безопасный повтор подтверждения,
  шестой — снятие публикации и HTTP 410 закрытой записи; седьмой —
  удаление без встреч, HTTP 204/404/409. Общий обзор API остаётся открытым.
- Открыто: [«Какие границы модулей обеспечат атомарность бронирования?»](issues/07-booking-boundaries.md).
  Инварианты реализованы для подтверждения: общий mutex календаря,
  независимые доменные правила и конструктор приложения с источником времени.
  Снятие публикации и удаление с проверкой всех встреч используют тот же
  mutex; общий обзор границ полного MVP по карте остаётся открытым.
- Открыто: [«Как одинаково запускать MVP локально и в Docker?»](issues/08-local-and-docker-runtime.md).
  В восьмом срезе выбраны Compose с готовностью, Nginx-прокси API и
  документации, порты/переменные и отдельная контейнерная приёмка.
  Общий обзор требований запуска карты остаётся открытым.
- Открыто: [«Какие проверки доказывают готовность MVP?»](issues/09-acceptance-criteria.md)
  и [«Достаточна ли итоговая спецификация для реализации MVP?»](issues/10-specification-review.md).
