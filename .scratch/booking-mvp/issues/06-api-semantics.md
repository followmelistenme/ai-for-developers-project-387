# Какой API покрывает согласованные сценарии MVP?

## Question

Опирается на решения
[о типах встреч](01-meeting-type-lifecycle.md),
[данных гостя и связи](02-guest-contact-data.md),
[повторном подтверждении](03-booking-retries.md),
[экранах владельца](04-owner-experience.md)
и [пути гостя](05-guest-experience.md).

Как выразить согласованные действия гостя и владельца в REST API,
чтобы контракт однозначно задавал данные, время, результаты и ошибки?

Согласовать операции и стабильные operationId, именованные схемы,
поля запросов и ответов, идентификаторы, формат дат и времён,
правила выдачи слотов и списка предстоящих встреч. Для ошибок определить
HTTP-статусы и данные, позволяющие показать нужное состояние интерфейса.

В частности, определить ответ при конфликте: какие обновлённые слоты
он содержит и для какого диапазона; как выражаются устаревший тип встречи,
недопустимый интервал, ошибка полей и повтор попытки бронирования.
Проверить, что публичные ответы не раскрывают лишних контактных данных.

Результат — спецификация операций и примеры обмена для будущего
`api/openapi.yaml`. Сохранить ADR-0001, отдельную runtime-валидацию,
`/openapi.json`, `/openapi.yaml` и `/docs`. Контракт и код не генерировать.

## Comments

### 2026-11-15 — согласован API первого среза

- `GET /api/owner/meeting-types` — список типов владельца, включая пустой.
- `POST /api/owner/meeting-types` — создание черновика из названия,
  необязательного описания и длительности в минутах.
- Сервер назначает уникальный идентификатор и состояние `draft`;
  успешное создание возвращает HTTP 201 с созданным типом.
- Ошибка данных — HTTP 400 с сообщением и ошибками по полям.
- Ограничения полей остаются согласованными ранее. Редактирования
  и публичного доступа к черновикам нет.

Пользователь подтвердил этот контракт для реализации первого среза;
задача остаётся открытой для API остальных сценариев MVP.

### 2026-11-15 — технический контракт второго среза

Для запрошенной пользователем реализации публикации и выбора типа:

- `POST /api/owner/meeting-types/{meetingTypeId}/publish` без тела —
  HTTP 200 с опубликованным типом, повтор возвращает тот же тип
  без повторного создания; неизвестный идентификатор — HTTP 404.
- `GET /api/meeting-types` — только опубликованные типы, включая пустой список.
- `GET /api/meeting-types/{meetingTypeId}` — опубликованный тип;
  неизвестный идентификатор и черновик — HTTP 404.

Это обратимые технические решения второго среза. Семантика повторов
публикации не разрешает вопрос повторного бронирования; задача карты
остаётся открытой для операций остальных сценариев.

### 2026-11-15 — технический контракт третьего среза

Добавляется `GET /api/meeting-types/{meetingTypeId}/slots` с необязательным
параметром `date` (YYYY-MM-DD). Без него выбирается первый день текущего
московского окна записи. HTTP 200 содержит серверное время, часовой пояс,
первую и последнюю даты окна, выбранную дату и интервалы слотов;
начала и окончания передаются в RFC 3339. Неверная дата или выход за окно —
HTTP 400, черновик или неизвестный тип — HTTP 404.

Серверное поле `nextWindowUpdate` задаёт точный момент следующего сдвига
окна, чтобы браузер мог обновить данные независимо от своего часового пояса.

Это чтение доступности, а не резервирование или создание встречи.
Семантика подтверждения и повторного бронирования остаётся открытой.

### 2026-11-15 — технический контракт четвёртого среза

Для запрошенного подтверждения встречи добавляются:

- `POST /api/meeting-types/{meetingTypeId}/meetings` (`confirmMeeting`):
  обязательные `start`, `guestName`, `guestEmail`; окончание и длительность
  определяются сервером. HTTP 201 содержит созданную встречу с типом,
  московской датой и интервалом, контактами и демонстрационной ссылкой.
  HTTP 400 — ошибки полей или интервала; HTTP 404 — неизвестный либо
  неопубликованный тип. HTTP 409 — сообщение о конфликте и `availability`
  с актуальными слотами выбранной московской даты без контактов.
- `GET /api/owner/meetings` (`listOwnerMeetings`): общий список встреч
  с окончанием позже текущего времени, по началу от ближайшей. Содержит
  подтверждённые пользователем поля типа, даты, интервала, контактов и ссылки.

Проверка пересечений и сохранение атомарны для всего календаря.
Расширенная семантика повторов остаётся отдельным решением: этот контракт
не обещает идемпотентность или восстановление ответа после потери связи.

### 2026-11-15 — технический контракт пятого среза

`confirmMeeting` требует UUID `attemptId` вместе с прежними полями.
Повтор успешного идентификатора с теми же типом, моментом начала,
обрезанными по краям именем/email возвращает HTTP 201 с исходной встречей.
Email сравнивается точно. Иные данные с сохранённым идентификатором —
HTTP 400 с `fields.attemptId`, без контактов или ссылки прежней встречи.
Новая попытка другого гостя на занятый слот — прежний HTTP 409
с актуальной доступностью без чужих данных.

Успешный результат удерживается до перезапуска, не истекает при сдвиге
окна или окончании встречи; ошибки не связывают идентификатор.
Повторы проверяются атомарно вместе с общим календарём. Нового маршрута
восстановления и сохранения запроса в браузере не добавляется.
Это реализация [согласованного решения о повторах](03-booking-retries.md).

### 2026-11-15 — технический контракт шестого среза

- `withdrawOwnerMeetingType`: `POST /api/owner/meeting-types/{meetingTypeId}/withdraw`
  без тела; HTTP 200 с `withdrawn`, повтор возвращает тот же тип.
  Черновик — HTTP 409, неизвестный ID — HTTP 404.
- `publishOwnerMeetingType` для `withdrawn` — HTTP 409 без обратного перехода.
- Гостевые чтение типа, слоты и новое подтверждение по `withdrawn` —
  HTTP 410 с сообщением «Запись на этот тип встречи закрыта».
  Черновик и неизвестный ID сохраняют HTTP 404. Каталог — только published.
- Атомарное снятие публикации упорядочено с новым бронированием.
  Успешный повтор из задачи 05 проверяется первым и возвращает прежний
  HTTP 201 без создания встречи, даже если публикация уже снята.
  Изменённые данные сохранённой попытки остаются ошибкой без чужих сведений.

Это обратимые технические формы ранее согласованного жизненного цикла.
Удаление типа относится к следующей задаче реализации.

### 2026-11-15 — технический контракт седьмого среза

`DELETE /api/owner/meeting-types/{meetingTypeId}` (`deleteOwnerMeetingType`),
без тела: HTTP 204 без ответа при удалении любого состояния без встреч,
HTTP 404 для неизвестного/уже удалённого ID, HTTP 409 с именованной схемой
`MeetingTypeDeletionConflict` и сообщением «Нельзя удалить тип встречи,
по которому есть встречи». Проверяются все встречи, включая прошедшие.
Гостевые чтение/слоты/новое подтверждение старого ID — HTTP 404;
публикация и снятие удалённого типа также не восстанавливают его.
Контракт изменён первым; Go/TypeScript сгенерированы. HTTP-проверка валидирует
реальный 409 по опубликованному `/openapi.json`, включая целую строку ошибки.
Сводный обзор всего API карты остаётся открытым.
