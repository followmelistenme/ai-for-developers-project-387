# 08: Запуск в Docker

Status: ready-for-agent
State: closed

**Source:** [MVP сервиса бронирования звонков](../../booking-mvp/spec.md).

**What to build:** разработчик запускает оба сервиса через Docker Compose
и проходит из браузера полный сценарий создания типа, публикации и записи
с просмотром встречи владельцем. Локальный запуск продолжает работать.

**Blocked by:** 04: [«Подтверждение встречи»](04-confirm-meeting.md).

- [x] Для обоих сервисов предоставлены Dockerfile и совместный запуск через Compose с согласованными требованиями к готовности и запуску.
- [x] Порты и адрес API настраиваются через окружение с согласованными значениями по умолчанию; адреса доступны соответствующим потребителям — браузеру и сервисам внутри контейнерной сети.
- [x] Полный браузерный сценарий создание → публикация → выбор слота → подтверждение → список владельца работает в контейнерном запуске; прямое открытие и перезагрузка маршрутов интерфейса работают.
- [x] Проксирование либо CORS соответствуют итоговой спецификации; документация API и оба представления OpenAPI доступны через документированные адреса.
- [x] При часовом поясе окружения, отличном от московского, даты и время записи по-прежнему рассчитываются и отображаются в Europe/Moscow.
- [x] Перезапуск бэкенда очищает типы и встречи, показывает пустое состояние владельцу и не позволяет записаться по прежним ссылкам; постоянное внешнее хранилище не добавляется.
- [x] Документация содержит воспроизводимые команды локального и Docker-запуска, переменные, порты, адреса API и описание сброса данных.
- [x] Проверка запуска из чистого состояния демонстрирует полный сценарий из браузера; способ включения проверок Docker следует согласованной матрице приёмки. `mise run check` проходит.

## Answer

Реализовано в `codex/booking-draft-integration`, коммит `b38eddd`
(`Add container launch and browser acceptance`).

- Многоэтапные [backend/Dockerfile](../../../backend/Dockerfile) и
  [frontend/Dockerfile](../../../frontend/Dockerfile), узкие `.dockerignore`.
  Официальные multiarch-образы закреплены digest; Go 1.27.4 и Node 22.22.2
  соответствуют неизменённым версиям проекта. Backend запускает статический
  бинарник без привилегий; постоянное хранилище не добавляется.
- [Compose](../../../compose.yaml) поднимает оба сервиса с healthcheck:
  API готов после успешного чтения списка типов, фронтенд — после проверки
  главной и проксированного API; запуск фронтенда ждёт готовности API.
  Бэкенд слушает все интерфейсы контейнера. По умолчанию хостовые
  5173/8080 на 127.0.0.1; порты, адрес привязки, API_TARGET и TZ настраиваются.
  README различает адрес браузера и origin API внутри контейнерной сети.
- Nginx отдаёт SPA и поддерживает прямые маршруты/перезагрузку;
  проксирует `/api`, `/docs`, `/openapi.json`, `/openapi.yaml` с одного origin.
  API_TARGET применяется при запуске без пересборки. Динамическое DNS-разрешение
  сохраняет связь с API после его пересоздания. CORS не требуется.
- Данные и успешные попытки остаются в памяти. Перезапуск очищает типы,
  публикации и встречи; `/owner` пуст, старые detail/slots/confirm получают
  404. Московские правила/отображение проверены при UTC контейнеров
  и America/Los_Angeles браузера, без новых тестовых clock/reset endpoints.
- [docker-check](../../../scripts/docker-check.sh) и `mise run docker-check`
  собирают и запускают отдельный проект на свободных портах, проходят
  настоящим браузером весь путь бронирования без HTTP-перехвата в локальный API.
  При успехе/ошибке удаляют только собственные контейнеры, сеть и образы;
  при ошибке выводят состояние и логи. Обычные Playwright-тесты исключают
  контейнерные сценарии, `mise run check` не требует Docker Engine.
  В Quality CI добавлен отдельный `Container acceptance` job с этой командой.
- [README](../../../README.md) содержит воспроизводимые команды локального
  и Docker-запуска, зависимости, переменные/порты, адреса документации,
  readiness, пересоздание, сброс данных и проверку. `.env` исключён из Git.

TDD выполнен на ранее согласованных публичных HTTP/браузерных границах.
Первый контейнерный сценарий падал с ECONNREFUSED до стека, затем прошёл
после реализации контейнеров/прокси/готовности. Далее добавлены браузерный
путь и сброс данных, затем проверка runtime API_TARGET реальным 502
с восстановлением без пересборки.

Три контейнерных сценария проверяют чистый запуск, HTTP/документацию,
прямые маршруты и перезагрузку; создание → публикацию → выбор → подтверждение →
список владельца; альтернативные порты/адрес API, одинаковый origin всех
браузерных API-запросов, московское время, сброс после restart и восстановление
после recreate API. Неверный API_TARGET даёт 502 для API/документации,
при этом SPA работает; возврат правильного адреса восстанавливает API.
