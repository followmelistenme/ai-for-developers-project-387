# Как владелец открывает управление и просматривает предстоящие встречи?

## Question

Опирается на решения
[«Как владелец управляет типами встреч в MVP?»](01-meeting-type-lifecycle.md)
и [«Какие данные гостя нужны для записи и самого звонка?»](02-guest-contact-data.md).

Какие экраны и переходы нужны владельцу для согласованных действий
с типами встреч и просмотра общего списка предстоящих встреч?

На грубом прототипе согласовать точку входа без авторизации, навигацию,
формы, сообщения проверки данных и пустые состояния. Определить состав
строки встречи, сортировку, включение уже начавшихся встреч и обновление
списка при новых бронированиях. Все даты и время — в часовом поясе календаря.

Явно согласовать доступность функций владельца при отсутствии авторизации;
не добавлять скрытую модель безопасности, аккаунты или личный кабинет.
Показать десктопный и мобильный варианты в стиле существующей главной.

Результат — ссылка на прототип и ответ пользователя по устройству экранов.
Рабочий интерфейс и API в этой задаче не реализуются.

## Comments

### 2026-11-15 — согласована часть для первого среза

Пользователь подтвердил `/owner`, ссылку «Для владельца» в шапке,
список типов встреч и кнопку «Создать тип встречи», предложение создать
первый тип в пустом состоянии, без авторизации. Это позволяет реализовать
создание черновика; задача остаётся открытой для остальных экранов владельца.

### 2026-11-15 — согласован список встреч для четвёртого среза

При запросе `implement-spec 04` пользователь подтвердил показ будущих
и ещё идущих встреч (окончание позже текущего времени), ближайшие сверху.
Поля: тип, дата и интервал по Москве, имя и email гостя, ссылка звонка.
Список общий для всех типов; размещается на существующем `/owner`.
Обновление при открытии, возврате фокуса и вручную — технический выбор
данного среза. Остальные экраны и действия карты остаются отдельными задачами.

### 2026-11-15 — шестой срез: окончательное снятие публикации

Запрос `implement-spec 06` добавляет действие «Снять публикацию»
у опубликованного типа в существующем `/owner`. Поясняется окончательность
и сохранение встреч. Успех меняет карточку на «Снят с публикации»,
без повторной публикации; состояние сохраняется после перезагрузки.
Новые экраны не вводятся. Остальные вопросы карты остаются открытыми.

### 2026-11-15 — седьмой срез: удаление без встреч

Запрос `implement-spec 07` добавляет «Удалить» у каждого состояния типа
в `/owner`, пояснение запрета при любых встречах, состояние ожидания и повтор
после ошибки сети. Успех убирает карточку; после потери успешного ответа
повторный 404 тоже убирает её. Запоздалые ответы публикации/снятия не возвращают
удалённую карточку и не подменяют итог удаления. При 409 показывается причина,
а для опубликованного типа остаётся «Снять публикацию». Мобильные состояния
проверены на 320/390 px. Общий обзор прототипа карты остаётся открытым.
